当前数据；不以 localStorage 替代账本数据库；补充有实际价值的仓储/迁移集成测试并记录真实结果。

## 4. 数据库版本与数据约束

**dbSchemaVersion = 1**（`AppMeta` 与 `PRAGMA user_version` 同写）。核心表：`app_meta`、
`ledger`、`category`、`"transaction"`、`audit_event`、`mutation_receipt`、`backup_record`、
`migration_record`。全部使用 STRICT 表、外键 `RESTRICT`、CHECK 约束与条件唯一索引；
审计/收据/迁移记录有触发器禁止 UPDATE/DELETE（追加型）。

| 域 | 实现约束 | 主要落点 |
|---|---|---|
| 金额 | `amount_fen` INTEGER 1～999999999；服务拒绝 0/负数/小数/非安全整数/超上限 | `src/shared/amount.ts`、`transaction-repo`、schema CHECK |
| 日期 | 真实公历 1900-01-01～9998-12-31；筛选 end 允许 9999-01-01 哨兵 | `src/shared/date.ts`、schema GLOB/CHECK |
| 时刻/精度 | `date` 必须无时刻，`minute` 必须有合法 HH:mm；正式交易不接受 unknown | schema CHECK + `isPrecisionConsistent` |
| 文本 | NFC + 首尾去空白、码点长度、空可选转 null、备注允许换行/Tab、其他控制字符拒绝 | `src/shared/text.ts`、schema length CHECK |
| 账本 | 单一 `default_key='default'`、CNY、Asia/Shanghai、dataRevision/datasetRevision | schema UNIQUE + 服务 |
| 分类 | 同账本规范化名称唯一（含停用）、`system_key` 唯一、sortOrder 0～999999、500 上限、其他不可停用 | schema 唯一索引 + 服务校验 |
| 交易 | 外键同账本分类；`source=manual` 无候选、`source=ai` 必有候选；候选关联唯一（含软删）；version 1～2147483647；软删/恢复 CAS | schema CHECK/复合外键/条件唯一索引 + 服务 |
| 审计/幂等 | 审计追加型；`(ledgerId,operation,mutationId)` 唯一收据；同键同载荷回放、不同载荷 `IDEMPOTENCY_CONFLICT` | schema + `ledger-service.runMutation` |
| revision | 每次实际业务变更 +1（同事务）；无变化/回放不加；超安全整数拒绝 | `bumpRevision` |

`mutation_receipt` 另存 `revision_at_commit`（内部列，不跨 IPC），用于回放时返回原 revision。

## 5. 迁移、备份与恢复

- 启动：单实例锁 → 校验/读取 `data/active.json` → 打开 `data/generations/<uuid>/ledger.db`
  （WAL、foreign_keys=ON、synchronous=FULL、busy_timeout=5000）→ 迁移 → 幂等默认账本 →
  业务完整性检查。active 指针缺失/损坏、存在无指针 generation、schema 过新、checksum 不符
  均拒绝启动或进入 recovery 模式，不创建空库覆盖。
- 迁移：逐级执行并写 `migration_record`（from/to/appVersion/checksum/backupId/status）；
  升级前做 `pre_migration` 一致快照；失败回滚事务、写 failed 记录并标记 `recovery_required`，
  业务写入返回 `RECOVERY_REQUIRED`，读取/备份/恢复仍可用；`migrating` 崩溃状态下次启动复位为 clean。
- 备份：`VACUUM INTO` 一致快照 → 写 `bk-backup.v1` 清单 → quick_check → 原子改名 →
  同事务登记 `backup_record`；档案为单文件 `backups/<uuid>.bkdb`，不含密钥/日志。
- 恢复：预览（hash/清单/schema/完整性）→ commit 再校验 + `pre_restore` 备份 →
  复制到新 generation staging → staging 迁移/业务校验 → 原子切换 active 指针 → 打开新库、
  更换 dataEpoch、写审计/收据与 `restore-log.jsonl`。失败保持旧 active 与旧库，staging 不生效。
- 回滚/恢复办法：迁移失败时从 `backup_record.kind='pre_migration'` 的档案走恢复流程；
  恢复失败时旧 generation 与 `pre_restore` 档案仍在 `backups/`，可按备份记录再次预览恢复。
  以上两条路径在集成测试中真实执行（见 §8）。
